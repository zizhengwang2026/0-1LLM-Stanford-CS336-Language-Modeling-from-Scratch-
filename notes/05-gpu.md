## 一、为什么大模型离不开 GPU

先讲个直觉：**CPU 像一位样样精通的老教授**，什么事都能干，但一次只能盯一两件事；**GPU 像一万个小学生在做口算**，单个不聪明，但一起算乘法快得离谱。

大模型训练本质就是"超多矩阵乘法 + 超多数据"。这种**高度重复、可以并行**的活，正好对 GPU 的胃口。所以：

- 训练一个 7B 模型，用 CPU 可能要几年；用几十张 GPU，几周就能跑完。
- 世界上 99% 的大模型算力，都长在 NVIDIA GPU（或它的平替）上。

> CS336 的视角：我们不只要"会用 GPU"，更要会**算账**——这张卡有多少算力、多少显存、传输多快，决定了你的模型能不能放下、训练要多久。

---

## 二、GPU 长什么样：从 SM 到 warp

以 A100 为例，GPU 内部是这样一层层组织的（**SM → Block → Warp → Thread**）：

| 名词 | 是什么 | 大白话比喻 |
|------|--------|-----------|
| **Thread（线程）** | 最细的计算单元，对应一个"算一个格子的人" | 一个小学生做一道口算 |
| **Warp（线程束）** | 固定 **32 个线程**绑在一起，锁步执行同一条指令 | 32 个小学生排成一排，老师喊"乘"，大家一起乘 |
| **Block（线程块）** | 程序员指定的线程组（比如 256 个线程），会被整体丢到一个 SM 上 | 一个"小组"，小组内可以互相借东西（共享内存） |
| **SM（流式多处理器）** | GPU 的"原子计算工厂"。A100 有 **128 个 SM**，每个 SM 含 64 个 CUDA 核心 + 4 个 Tensor Core | 一栋楼里的一个车间，车间里有很多工人 |
| **SIMT** | 单指令多线程：一个 warp 里 32 个线程跑同一条指令、但处理不同数据 | 老师同一句话，32 个学生算不同的数 |

**两个关键坑**：

1. **分支发散（control divergence）**：如果代码里有 `if`，warp 里一部分线程走 if、一部分走 else，GPU 会**串行**把两条路都跑一遍（用掩码屏蔽另一半）。等于"本来一起算，现在排队算"，变慢。
2. **warp 是调度最小单位**：你写的线程数最好能整除 32，不然最后一组凑不满 32 个，剩下的槽位空转浪费。

## 三、GPU 的内存金字塔

GPU 上有好几层"仓库"，越靠近计算核心越快、越小、越贵：

| 层级 | 容量（A100） | 带宽 | 延迟 | 谁能用 | 大白话 |
|------|------------|------|------|--------|--------|
| **寄存器** | 256KB/SM | ~10 TB/s | 1 周期 | 单个线程私有 | 你手边的草稿纸，最快 |
| **L1 / 共享内存** | 192KB/SM | ~1 TB/s | 20–40 周期 | 同一 Block 内 | 小组共用的白板 |
| **L2 缓存** | 40 MB（整卡） | ~3 TB/s | ~200 周期 | 所有 SM 共享 | 楼层公共储物间 |
| **HBM（显存）** | 40/80 GB | ~2 TB/s | ~500 周期 | 全部线程可见 | 楼下大仓库，大但慢 |
| 常量内存 | 64 KB | 广播 | ~5 周期 | 只读 | 公告栏 |

> **为什么分这么多层？** 一句话：**速度、容量、成本不可兼得**。寄存器最快但贵到离谱（约 100 万美元/GB），HBM 便宜但慢。GPU 用"快的小仓库 + 慢的大仓库"的组合，靠"把常用数据搬上来、算完再存回去"来平衡。

**对训练的直接影响**：参数量和梯度通常都存在 **HBM（显存）** 里，所以"显存不够"= 大仓库放不下 = 模型跑不了。后面所有分布式、重计算技巧，核心都是"怎么少占 HBM"。

## 四、算力 vs 带宽的"剪刀差"：内存墙

一个残酷的事实（屋顶线模型 Roofline）：

- 从 K20 到 H100，**算力涨了上万倍**，但**显存带宽只涨了百倍**，芯片间互联更慢。
- 结果：很多操作不是"算得慢"，而是"**数据从 HBM 搬到 SM 的路上堵车了**"。

怎么判断一个操作卡在哪？看**算术强度（Arithmetic Intensity）= FLOPs ÷ 访问的字节数**：

- 算术强度高（如矩阵乘）→ **计算受限**，GPU 爽。
- 算术强度低（如逐元素加、激活函数）→ **内存受限**，GPU 在干等数据。

> CS336 的核心一句话：**优化大模型，本质是优化"内存搬运"，不是优化"计算本身"**。后面的算子融合、分块，全是为了提高算术强度、少搬数据。

## 五、六大性能优化技术

| 技术 | 干什么 | 为什么快 |
|------|--------|----------|
| **1. 避免串行分支** | 少用 `if/else`、循环里别让 warp 发散 | 防止 32 线程排队跑两条路 |
| **2. 低精度** | FP32 → BF16/FP16 → FP8/INT8 | 每个数占的字节少了，带宽和算力都翻倍（A100 上 FP16 的 Tensor Core 算力是 FP32 的 **16 倍**） |
| **3. 算子融合 Fusion** | 把"乘→加→激活"多个操作合成一个 CUDA 核 | 中间结果不用写回 HBM 再读出来，省掉来回搬运，提速 2–5 倍 |
| **4. 重计算 Recomputation** | 前向不存激活，反向时重新算一遍 | 用"过剩的算力"换"紧缺的显存"，典型如梯度检查点 |
| **5. 内存合并 Coalescing** | 让一个 warp 的线程访问**连续**地址 | 32 次零散读取合成 1 次突发传输，吞吐可差 4 倍 |
| **6. 分块 Tiling** | 矩阵乘切成小块放进共享内存再算 | 全局内存读取次数从 N² 级降到 N 级 |

> **低精度举例**：GPT-3 175B 用 FP32 要 700GB 显存，用 BF16 只要 350GB——直接省一半仓库。

## 六、FlashAttention：把 Attention 塞进 SRAM

普通 Attention 要先算一个 N×N 的完整注意力矩阵，写出来存到 HBM，再读回来做后续。N 一大，这个矩阵和 HBM 读写都爆了。

**FlashAttention 的核心思想**：不写出完整 N×N 矩阵，而是**分块（tile）**，每次只把一小块 Q/K/V 搬进超快的 SRAM，在 SRAM 里就算完"这块对这块"的 softmax 和加权求和，结果直接累加输出。显存占用从 O(N²) 降到 O(N·d)。

| 版本 | 突破点 | 效果 |
|------|--------|------|
| **V1** | 分块 + online softmax（流式更新最大值和累计和），全程不写完整矩阵 | 解决 IO 瓶颈，显存线性 |
| **V2** | 调整为 Q 外循环、KV 内循环，并做 split-KV 并行 | 更贴合 Tensor Core，A100 上比 V1 快 1.7–2 倍 |
| **V3** | 利用 H100 的异步 WGMMA + 双缓冲，计算和搬数据重叠；原生 FP8 | SM 利用率 80%+，FP8 比 V2 又快 1.5–2 倍 |

> 一句话记忆：**V1 解决"别写大矩阵"，V2 解决"算得不够并行"，V3 解决"计算和搬运重叠"**。

## 七、PagedAttention：让显存像虚拟内存一样分页（推理）

这是**推理阶段**的显存管理技巧（vLLM 提出），和 FlashAttention 互补：

- **问题**：自回归生成时，每生成一个 token 都要把它的 K、V 存进 **KV Cache**。传统做法预先连续分配一大块（比如预留 2048 个位置），你实际只用 300 个 → **内部碎片**；多个请求零散的空闲对不上 → **外部碎片**。
- **解法**：把 KV Cache 切成固定大小的"页"（如每页 16 个 token），用页表把"逻辑页"映射到"物理页"，物理上可以不连续。浪费只有不到一页。
- **和 FlashAttention 的区别**：FlashAttention 改的是**怎么算**（kernel 更快），PagedAttention 改的是**怎么存**（显存更省）。推理时两者可以配合。

## 十、常见坑 & 面试可能问

1. **"为什么大模型训练显存总不够？"** → 不只是参数，还有**梯度 + 优化器状态 + 激活值**三座大山（下一讲细算）。
2. **"FlashAttention 是近似算法吗？"** → 不是，结果是**精确**的，只是不写出完整注意力矩阵，省的是 IO 不是精度。
3. **"算术强度低的操作怎么办？"** → 算子融合，把多个内存受限操作合成一个，减少 HBM 往返。
4. **"GPU 和 TPU 区别？"** → GPU 通用（有 warp、能跑各种核），TPU 是 Google 专用 ASIC（只为矩阵乘优化，架构更简洁）。
