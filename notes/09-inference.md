# 第9讲 · 模型推理 Inference（CS336 L10 × DIY-LLM 第10章）

> **本讲位置**：CS336 **Systems → 落地** 的关键一环。前面花大力气“训出”模型，这一讲讲“怎么让它又快又便宜地回答问题”——这是产品能不能用的分水岭。
>
> **一句话定位**：训练是“一次性的重活”，推理是“每天几亿次的细活”。优化目标从“算得快”变成“又便宜、又低延迟、又能扛高并发”。
>
> **难度评级：🟠 偏难**。它需要你建立“算术强度 / 显存带宽”的直觉，理解为什么 Decode 阶段会卡在“搬数据”而不是“算”。概念本身不难，但第一次接触容易和训练混。

---

## 🔤 先扫盲：重点术语大白话

| 术语 | 大白话 |
|------|--------|
| **推理 Inference** | 模型训好了，拿它来“答题/干活”的过程。训练=学习，推理=考试。 |
| **自回归 Autoregressive** | 一个字一个字往外吐，后一个字要等前一个字出来才能写。像写作文，得先有上一句才有下一句。 |
| **Prefill 预填充** | 你发一大段提问，模型先把这整段“读一遍、算出每个字的理解(K/V)”，这步叫预填充。 |
| **Decode 解码** | 预填充完后，模型开始一个字一个字往外生成回答，每吐一个字叫一步 Decode。 |
| **KV Cache** | “阅读理解笔记”。模型读每个字时记两样东西：K=Key(这字和谁有关)、V=Value(这字具体信息)。生成新字要回头看这些笔记，不存就得重读，太慢，所以缓存。 |
| **TTFT** | Time To First Token，首字延迟。你提问后，等到第一个字蹦出来花了多久。 |
| **ITL / TPOT** | Inter-Token Latency，字间延迟。生成时每两个字之间隔多久（决定“打字机”流不流畅）。 |
| **吞吐量 Throughput** | 整个系统 1 秒能吐多少字（所有用户加起来）。 |
| **算力受限 compute-bound** | 活儿主要卡在“算得够不够快”。 |
| **显存带宽受限 memory-bound** | 活儿主要卡在“数据从显存搬进计算单元够不够快”。 |
| **算术强度** | 每搬 1 字节数据，能做多少次计算。越高越偏向算力受限。 |
| **投机解码** | 让小模型先快速打草稿，大模型只负责“批改”，省掉大模型自己慢慢写的时间。 |
| **量化** | 把数字从“高精度(16位)”压成“低精度(8位/4位)”，占空间小一半、搬得快一倍，但可能略掉精度。 |
| **PagedAttention** | 把 KV Cache 像电脑虚拟内存一样分页管理，减少碎片浪费（vLLM 核心）。 |
| **Continuous Batching** | 动态批处理：谁生成完了立刻腾位置给新请求，GPU 不空转。 |

**记住这条主线**：推理 = 先把问题读一遍(Prefill) → 再一个字一个字写答案(Decode) → 写每个字都要翻前面的笔记(KV Cache) → 想快就得解决“搬笔记太慢”(memory-bound) 的问题。

## 一、推理和训练到底哪里不一样（小例子带入）

**小例子**：句子“猫 吃 鱼”。

- **训练时（有标准答案）**：老师给你完整句子“猫 吃 鱼”，让你同时算“猫”应该预测“吃”、“吃”应该预测“鱼”。所有位置**并行**算，因为答案已知。
- **推理时（没答案）**：你只给了“猫 吃”，模型要**自己猜**下一个字。它先算出“鱼”的概率最高，吐出“鱼”；然后拿“猫 吃 鱼”再去猜下下个字……**必须等前一个字出来才能算后一个**，天然串行。

| 维度 | 训练 | 推理 |
|------|------|------|
| 数据流 | 整段一次算完（答案已知，可并行） | 自回归，一个 token 一个 token 吐（串行） |
| 瓶颈 | 算力 + 通信 + 显存(激活/梯度/优化器) | **显存容量 + 带宽**(KV Cache 越攒越大) |
| 目标 | 把 loss 降到最低 | TTFT 快、吞吐高、单请求延迟低 |

> 一句话：训练是“开卷考试全班一起做”，推理是“闭卷一个字一个字写”。

## 二、推理的两个阶段：Prefill 与 Decode（逐步走一遍）

**小例子**：你问“中国的首都是”，模型要答“北京”。

**阶段 1 · Prefill（读题）**：
1. 把 prompt “中国的首都是”这 6 个字，一次性送进模型。
2. 模型对这 6 个字做完整注意力计算，算出并**缓存**每个字的 K、V。
3. 此时 KV Cache 里有 6 份笔记。

**阶段 2 · Decode（写答案，逐字走）**：
- 第 1 步：拿“首都”的语义当 Query，去和缓存里 6 份 K/V 做注意力，预测下一个字概率最高是“北” → 吐出“北”，把“北”的 K/V 追加进缓存（缓存变 7 份）。
- 第 2 步：拿新上下文，预测下一个是“京” → 吐出“京”，缓存变 8 份。
- 第 3 步：预测下一个是“。”或结束符 → 停止。

注意力公式不变：`Attention(Q,K,V) = softmax(QKᵀ/√d_k) V`。区别只在 Decode 每次**只进 1 个新 query**（“北”那个字），但要跟前面所有缓存的 K/V 算。

> **为什么分两个阶段很重要**：Prefill 是“一口气读很多字”→ 算得满；Decode 是“一次只写 1 个字”→ 大部分时间在等数据。后面优化全围绕这个差异。

## 三、KV Cache：推理的“显存杀手”（逐行代码看它怎么长大）

**为什么需要它**：自回归每生成一个字，都要和前面所有字做注意力。如果每次都重新算前面所有字的 K/V，开销爆炸。所以把历史 K/V **缓存**复用。

**它有多大**：显存 ∝ `token数 × 层数 × 注意力头数 × 隐藏维度`。序列越长、模型越大，越夸张。

下面用极简代码**逐行**演示 Decode 时 KV Cache 怎么一步步长大：

```python
# 演示 Decode 阶段：KV Cache 怎么随生成一步步变大
# 极简设定：模型 1 层、1 个注意力头、隐藏维度 2（只为看清原理，真实是几千维）

# 初始：prompt 两个 token '你' '好'，Prefill 已算好它们的 K/V
kv_cache = [
    {'k': [0.1, 0.2], 'v': [0.3, 0.4]},  # 第1个 token '你' 的 K/V 笔记
    {'k': [0.5, 0.6], 'v': [0.7, 0.8]},  # 第2个 token '好' 的 K/V 笔记
]

# ---- 第 1 步 Decode：要生成第 3 个 token ----
new_kv = {'k': [0.9, 1.0], 'v': [1.1, 1.2]}  # 模型算出 '，' 这个字的 K/V
kv_cache.append(new_kv)                       # 把新笔记追加进缓存
print(len(kv_cache))                          # 输出：3  —— 缓存从 2 涨到 3

# ---- 第 2 步 Decode：生成第 4 个 token ----
new_kv = {'k': [1.3, 1.4], 'v': [1.5, 1.6]}  # 算出 '世' 的 K/V
kv_cache.append(new_kv)
print(len(kv_cache))                          # 输出：4  —— 每生成一个字，缓存 +1
```

**逐行说明**：
- 第 4–7 行：缓存一开始装了 prompt 两个字的笔记。
- 第 12 行：`append` 是重点——每生成一个新字，就要把它的 K/V 存起来，否则下一步还要重算。
- 第 13/18 行：打印证明缓存长度随生成线性增长。**这正是问题所在**：生成 1000 字就要存 1000 份笔记，显存吃紧。

> **补一刀（见第5讲）**：PagedAttention(vLLM) 把 KV Cache 像虚拟内存分页，碎片浪费压到不到一页，并发能力大增。这是工业界推理引擎事实标准。

## 四、算力受限 vs 显存受限（用“算术强度”小推导）

**核心指标：算术强度 AI = 这次计算做的总 FLOPs / 这次从显存搬进来的字节数**。

**小推导（Decode 阶段，batch=1）**：
- 假设模型 7B 参数，每个参数 2 字节(FP16) → 权重共 14 GB。
- Decode 每步只生成 1 个 token，做约 `2 × 7B = 14 GFLOPs` 计算。
- 但这 14 GFLOPs 之前，得先把 14 GB 权重从显存(HBM)搬进计算单元。
- `AI = 14 GFLOPs / 14 GB = 1 FLOP/Byte`。
- **AI ≈ 1 意味着**：每搬 1 字节只做 1 次运算，远远低于 GPU 的“算力/带宽”比值（H100 约 286 TFLOPs / 3.35 TB/s ≈ 85）。所以 Decode **卡在搬数据** → **memory-bound（显存带宽受限）**。

**对比 Prefill（长 prompt，比如 1000 字）**：
- 一次算 1000 个 token，计算量 ≈ `2 × 7B × 1000 = 14 TFLOPs`，但仍只搬 14 GB 权重一次。
- `AI ≈ 14 TFLOPs / 14 GB = 1000 FLOP/Byte` → 远高于 85 → **compute-bound（算力受限）**，和训练类似。

**怎么改善 memory-bound？四条路**：
1. **增大 batch**（一次多算几个请求，14 GB 权重摊给更多人用，AI 升高）。
2. **GQA/MQA**（减少 KV 头数，少搬 KV Cache）。
3. **量化**（INT8/INT4，每个数占更少字节，搬得更快）。
4. **模型并行**（多卡拼出更大总带宽）。

> 一句话记忆：**Prefill 像“搬一次货、干一大票活”（算力受限）；Decode 像“反复搬同一批货、每次只干一点活”（带宽受限）。**

## 五、延迟 vs 吞吐量：两个容易混淆的指标（算给你看）

**小例子**：假设 TTFT=0.5 秒，ITL=0.05 秒，要生成 20 个字。
- **E2E 总延迟** = TTFT + 生成长度 × ITL = 0.5 + 20 × 0.05 = **1.5 秒**。
- **平均吞吐**（单请求）= 20 字 / 1.5 秒 ≈ **13.3 字/秒**。

| 指标 | 含义 | 受什么影响 |
|------|------|-----------|
| **TTFT** | 首 token 等待 | 排队 + Prefill 时长 |
| **ITL/TPOT** | 字间间隔 | Decode 速度（流式体验） |
| **E2E Latency** | 端到端总耗时 | TTFT + 生成长度 × ITL |
| **Throughput** | 系统整体 字/秒 | 批大小、GPU 利用率 |

> **高吞吐 ≠ 低延迟**。大 batch 拉高吞吐，但会拖慢单请求首字延迟。对话产品要在两者间取舍（比如付费用户用小 batch 保低延迟，离线批处理用大 batch 保吞吐）。

## 六、批处理与持续批处理（小例子对比）

- **静态 Batching**：把 4 个请求打包，等最慢的那个算完才一起返回。快的被慢的拖死（木桶效应）。
- **持续批处理（vLLM 标配）**：请求动态进出。请求 A 生成完了，立刻腾出位置塞进新请求 B，**GPU 几乎不空转**。

**小例子**：3 个请求分别要生成 10/50/20 个字。
- 静态批：总耗时 ≈ 最慢的 50 字对应的时间（前两个早完事也得等）。
- 持续批：第 1 个（10字）完了立刻接新请求，GPU 利用率显著提升，整体吞吐成倍涨。

> 配合 KV Cache 分页（PagedAttention），持续批处理才高效——否则碎片化的显存放不下新请求。

## 七、投机解码 Speculative Decoding（逐步走一遍，证明“无损”）

Decode 阶段大模型串行太慢。思路：“**小模型打草稿，大模型批改**”。

**小例子**（接前面的“中国的首都是”）：

```python
# 投机解码逐步演示（无损加速的核心思想）
prompt = '中国的首都是'

# 1) 小模型快速起草 3 个候选（小模型便宜，串行也不慢）
draft = LM_small.generate(prompt, n=3)   # 假设输出 ['北', '京', '市']

# 2) 大模型一次性并行验证这 3 个草稿（只做 1 次前向，不是逐个等）
#    大模型看：P('北'|prompt) 高 ✓接受；P('京'|上下文) 高 ✓接受；
#             P('市'|...) 低 ✗拒绝（大模型其实想接 '城'）
verified = LM_big.verify(prompt, draft)  # 返回：接受 ['北','京']，拒绝 '市'

# 3) 结果：这 1 步我们只做了 1 次大模型前向，却吐出了 2 个 token
#    原本要 2 次串行大模型前向；现在省了 1 次 —— 这就是加速
#    拒绝点由大模型自己采样接上：'城'
final = ['北', '京', '城']                 # 最终输出，和大模型自己一步步写完全一致
```

**逐行说明**：
- 第 5 行：小模型起草，便宜快速。
- 第 9 行：`verify` 是并行验证（一次性算 3 个位置），关键在“只花 1 次大模型前向的钱，验证 3 个 token”。
- 第 14 行：**无损的关键**——凡是被接受的 token，都是大模型自己概率分布里认可的；被拒的由大模型亲自接手。所以输出分布与原模型**完全一致**，只是更快。

DeepSeek 的 **MTP（Multi-Token Prediction）** 在训练时就让模型学会预测多个未来 token，给投机解码提供更准的“草稿”，进一步提速。

## 八、量化：用更少的比特换更大吞吐（小例子算字节）

训练用 BF16/FP16（每个数 2 字节），推理可以压到 INT8（1 字节）/ INT4（0.5 字节）。

**小例子**：7B 模型权重。
- FP16：7B × 2 字节 = **14 GB**。
- INT8：7B × 1 字节 = **7 GB**（显存/带宽直接减半）。
- INT4：7B × 0.5 字节 = **3.5 GB**（再减半）。

每少一半比特，KV Cache 和权重占用少一半，直接缓解 memory-bound（第四节说的“搬得更快”）。

- 常见算法：**GPTQ**、**AWQ**（都是“尽量不伤精度地压缩权重”的方法）。
- 取舍：压太狠(如 INT2)会掉精度，要在“省显存”和“保质量”间平衡。

> 一句话：量化 = 把“字”写小一点，搬到 GPU 里更快，但别小到认不出。

## 九、其他推理方向（了解即可）

- **状态空间模型 SSM（如 Mamba）**：用递归隐状态替代显式 KV Cache，长序列更省，但极长有记忆衰减。
- **扩散模型做语言**：块内并行生成、块间自回归，缓显存压力，长逻辑连贯性还在研究。
- **提示词压缩**：硬压缩（挑关键句）、软压缩（连续向量前缀），缩短初始 KV Cache。

## 十一、常见坑 & 面试深挖

1. **“为什么推理比训练慢在别的地方？”** → 训练算力受限，推理 Decode 显存带宽受限。
2. **“KV Cache 为什么占显存？”** → 随序列长度线性增长，∝ token×层×头×维度（第三节代码演示了“每生成一字 +1 份”）。
3. **“投机解码会改输出吗？”** → 不会，大模型验证保证输出分布与原模型一致（无损，第七节证明）。
4. **“TTFT 和 ITL 区别？”** → 首字等待 vs 后续字间隔，分别对应 Prefill 和 Decode 体验。
5. **“量化为什么能提速？”** → 每数占字节减半→显存/带宽占用减半→缓解 memory-bound（第八节算例）。
6. **“为什么增大 batch 能改善 Decode？”** → 把固定 14GB 权重的搬运摊给更多请求，算术强度升高，脱离纯带宽受限。
