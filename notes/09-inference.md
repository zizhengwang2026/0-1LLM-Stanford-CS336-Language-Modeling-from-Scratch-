# 第9讲 · 模型推理 Inference（CS336 L10 × DIY-LLM 第10章）

> **本讲位置**：CS336 **Systems → 落地** 的关键一环。前面花大力气"训出"模型，这一讲讲"怎么让它又快又便宜地回答问题"——这是产品能不能用的分水岭。
>
> **一句话定位**：训练是"一次性的重活"，推理是"每天几亿次的细活"。优化目标从"算得快"变成"又便宜、又低延迟、又能扛高并发"。

---

## 一、推理和训练到底哪里不一样

| 维度 | 训练 | 推理 |
|------|------|------|
| 数据流 | 整段序列一次算完（teacher-forcing，有真实标签） | 自回归，**一个 token 一个 token 吐**（时间上串行） |
| 瓶颈 | 算力（FLOPs、通信、激活/梯度/优化器显存） | **显存容量 + 带宽**（KV Cache 越攒越大） |
| 目标 | 把 loss 降到最低 | TTFT 快、吞吐高、单请求延迟低 |

> 训练时可以用真实标签"并行"算整句话；推理时你**不知道下一个 token 是啥**，只能生成上一个、再算下一个，天然串行。

---

## 二、推理的两个阶段：Prefill 与 Decode

一次对话生成，内部是两段完全不同的活：

1. **Prefill（预填充）**：把用户整段 prompt 一次性算完，算出并缓存所有 token 的 **K、V**（即 KV Cache）。
2. **Decode（解码）**：从第 1 个新 token 开始，每步拿"新 token 的 Q"去和缓存的 K/V 做 Attention，生成一个 token，再把它的 K/V 追加进缓存。

注意力公式不变：`Attention(Q,K,V) = softmax(QKᵀ/√d_k) V`，只是 Decode 阶段每次只进 1 个新 query。

---

## 三、KV Cache：推理的"显存杀手"

**为什么需要它**：自回归每生成一个 token，都要和前面所有 token 做注意力。如果每次都重新算前面所有 token 的 K/V，开销爆炸。所以把历史 K/V **缓存**起来复用。

**它有多大**：显存 ∝ `token数 × 层数 × 注意力头数 × 隐藏维度`。

- 序列越长、模型越大，KV Cache 越夸张。
- 这是推理显存的主要负担，也是很多优化的靶子。

> 补充（详见第5讲）：用 **PagedAttention（vLLM）** 把 KV Cache 像虚拟内存一样分页管理，能把显存碎片浪费压到不到一页，大幅提升并发。这是工业界推理引擎的事实标准之一。

---

## 四、算力受限 vs 显存受限（用算术强度判断）

核心指标还是**算术强度 AI = FLOPs / 搬运的字节数**：

- **Prefill（长 prompt）**：一次算很多 token，AI 高 → **compute-bound（算力受限）**，和训练类似。
- **Decode（batch 小、每次只 1 个新 token）**：AI ≈ 1（S≫1, T=1），主要时间在把权重和 KV Cache 从 HBM 搬进来 → **memory-bound（显存带宽受限）**。

怎么改善 memory-bound？四条路：
1. **增大 batch size**（一次多算几个请求，摊薄权重搬运）。
2. **GQA / MQA**（减少 KV 头数，少搬 KV）。
3. **量化**（INT8/INT4，每个数占更少字节）。
4. **模型并行**（多卡拼出更大总带宽）。

---

## 五、延迟 vs 吞吐量：两个容易混淆的指标

| 指标 | 含义 | 受什么影响 |
|------|------|-----------|
| **TTFT** | Time To First Token，首 token 等待时间 | 排队 + Prefill 时长 |
| **ITL / TPOT** | Inter-Token Latency，token 之间的间隔 | Decode 速度（流式体验） |
| **E2E Latency** | 端到端总耗时 | TTFT + 生成长度 × ITL |
| **Throughput** | 系统整体 token/s | 批大小、GPU 利用率 |

> **高吞吐 ≠ 低延迟**。大 batch 能拉高吞吐，但会拖慢单个请求的首字延迟。做对话产品要在两者之间取舍。

---

## 六、批处理与持续批处理（Continuous Batching）

- **静态 Batching**：固定把一批请求打包，等最慢的那个算完才一起返回——快的被慢的拖死。
- **持续批处理（vLLM/业界标配）**：请求动态进出，一个请求生成完了立刻腾出位置塞新请求，**GPU 几乎不空转**，吞吐成倍提升。

> 配合 KV Cache 分页（PagedAttention），持续批处理才能高效——否则碎片化的显存放不下新请求。

---

## 七、投机解码（Speculative Decoding）

Decode 阶段大模型串行太慢，于是"用小模型打草稿、大模型把关"：

- 一个**小模型**自回归地快速起草一串候选 token（草稿）。
- **大模型**一次性并行验证这串草稿，哪些对就收下，遇到第一个不对的就截断、由大模型自己接手。
- 效果：大模型实际执行的"串行步数"大幅减少，整体加速且**输出分布完全一致**（无损）。

DeepSeek 的 **MTP（Multi-Token Prediction）** 在训练时就让模型学会预测多个未来 token，为投机解码提供更好的"草稿表示"，进一步提速。

---

## 八、量化：用更少的比特换更大的吞吐

- 训练用 BF16/FP16，推理可以压到 **INT8 / INT4**（甚至更低）。
- 每少一半比特，KV Cache 和权重的显存/带宽占用就少一半，直接缓解 memory-bound。
- 常见算法：GPTQ、AWQ（都是"尽量不伤精度地压缩权重"的方法）。
- 取舍：压太狠会掉精度，要在"省显存"和"保质量"间平衡。

---

## 九、其他推理方向（了解）

- **状态空间模型（SSM，如 Mamba）**：用递归隐状态替代显式 KV Cache，长序列更省，但极长序列有梯度/记忆衰减问题。
- **扩散模型做语言**：块内并行生成、块间自回归，缓显存压力，但长逻辑连贯性还在研究。
- **提示词压缩**：硬压缩（挑关键句）、软压缩（连续向量前缀），缩短初始 KV Cache。

## 十一、常见坑 & 面试可能问

1. **"为什么推理比训练慢在别的地方？"** → 训练是算力受限，推理 Decode 是显存带宽受限。
2. **"KV Cache 为什么占显存？"** → 它随序列长度线性增长，且 ∝ token×层×头×维度。
3. **"投机解码会改输出吗？"** → 不会，大模型验证保证输出分布与原模型一致（无损加速）。
4. **"TTFT 和 ITL 区别？"** → 首字等待 vs 后续每个字间隔，分别对应 Prefill 和 Decode 的体验。
